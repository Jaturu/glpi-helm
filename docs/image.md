# The container image

`ghcr.io/jaturu/glpi` is built from [`image/`](../image) in this repository
specifically for this chart. It contains GLPI, php-fpm and the PHP CLI, and
nothing else. The nginx sidecar uses the upstream `nginxinc/nginx-unprivileged`
image.

## Contents

| Item | Value |
|------|-------|
| Base | `alpine:3.24` |
| PHP | Alpine's `php84`, `php84-fpm` and the extensions listed below |
| GLPI | The release named by `appVersion` in `charts/glpi/Chart.yaml` |
| Runs as | uid/gid 33 |
| Listens | php-fpm FastCGI on `127.0.0.1:9000` only |
| App path | `/var/www/glpi` |
| Data path | `/var/glpi` (`config/`, `files/`, `logs/`, `marketplace/`) |
| Command | `php-fpm --nodaemonize --force-stderr` |

The image ships no web server, no compiler toolchain and no Composer.

### PHP extensions

GLPI 12 supports PHP 8.3 to 8.5. The list below comes from
`src/Glpi/System/RequirementsManager.php` in the GLPI source.

| Group | Extensions |
|-------|------------|
| Required | bcmath, curl, dom, fileinfo, filter, gd, intl, libxml, mbstring, mysqli, openssl, session, simplexml, sodium, tokenizer, xmlreader, xmlwriter, zlib |
| Recommended | bz2, ctype, exif, iconv, ldap, opcache, phar, posix, zip |

Alpine compiles filter, hash, json, libxml and zlib into PHP. Each of the
others is its own `php84-<name>` package, named in the `PHP_PACKAGES` build
arg.

## Version: one source

The GLPI version is set only in `charts/glpi/Chart.yaml`:

```yaml
appVersion: "12.0.2"
```

- The Dockerfile's `GLPI_VERSION` build arg has no default. A build without
  it fails immediately.
- `make image` and CI read `appVersion` and pass it as the build arg and the
  image tag.
- The chart's `image.tag` defaults to `appVersion`.

So the chart's default image is always the image built from the same GLPI
release.

## How it is built

The [Dockerfile](../image/Dockerfile) has two stages.

build

1. Downloads the release archive `glpi-<version>.tgz` from the GLPI project's
   GitHub releases. The archive already contains `vendor/` and the compiled
   front-end assets, so no Composer or Node step is needed.
2. Makes the tree root-owned, removes the in-tree `files/` and `marketplace/`
   directories, and checks the archive holds the expected version.
3. Adds [`inc/downstream.php`](../image/glpi/downstream.php), GLPI's hook for
   packagers, which moves the data paths to `/var/glpi`.

runtime

1. Applies pending Alpine package updates, installs PHP, php-fpm and the
   extension packages, removes Alpine's default fpm pool, and verifies the
   key extensions load.
2. Installs the image's PHP configuration (below).
3. Copies the application in, owned by root. Only `/var/glpi` is owned by
   uid 33.
4. Switches to uid 33.

## Data paths

GLPI's defaults keep configuration, uploads and plugins inside the
application tree. `inc/downstream.php` sets four constants instead:

| Constant | Path |
|----------|------|
| `GLPI_CONFIG_DIR` | `/var/glpi/config` |
| `GLPI_VAR_DIR` | `/var/glpi/files` |
| `GLPI_LOG_DIR` | `/var/glpi/logs` |
| `GLPI_MARKETPLACE_DIR` | `/var/glpi/marketplace` |

GLPI loads `config/local_define.php` (generated by the chart) before
`inc/downstream.php`, and the file only defines a constant that is not yet
set. The chart refuses to override these four, because its volume mounts
depend on them.

## PHP configuration and load order

| Order | File | Set by |
|-------|------|--------|
| 1 | `/etc/php84/php.ini` | Alpine defaults |
| 2 | `/etc/php84/conf.d/99-glpi.ini` | Image: upload limits (50M), memory, session cookie flags, opcache, `expose_php = Off` |
| 3 | `/etc/glpi/php.d/*.ini` | Chart: upload limits from `glpi.uploadLimitMB`, timezone, `session.cookie_secure`, plus `php.extraIni` |

`PHP_INI_SCAN_DIR=":/etc/glpi/php.d"` appends directory 3 to the built-in
scan path. Later files win, so the chart's values override the image's
without depending on the PHP version in the path. Alpine uses one `php.ini`
and one `conf.d` for both php-fpm and the CLI, so `bin/console` and cron see
the same settings as the web requests.

php-fpm uses a single, complete config,
[`image/php/php-fpm.conf`](../image/php/php-fpm.conf): one pool, loopback
listener, no `user` / `group` directives (it runs as the container user), no
pid file, logs to stderr, and `ping` / `status` endpoints for the chart's
probes.

opcache runs with `validate_timestamps = 0`. The code never changes inside a
running container, so PHP doesn't stat files on each request. A new image
means a new pod and a fresh cache. Plugins installed from the marketplace are
new files, which opcache compiles on first use. A plugin updated in place is
picked up at the next pod restart.

## Building locally

```console
make version        # prints the GLPI version from Chart.yaml
make image          # builds glpi:dev and ghcr.io/jaturu/glpi:<version>
make test-image     # build + contract tests (see Testing)
```

Other build args, rarely changed:

| Arg | Default | Purpose |
|-----|---------|---------|
| `ALPINE_VERSION` | `3.24` | Alpine release for both stages |
| `PHP_VERSION` | `84` | Alpine's PHP package suffix. Must be a PHP version GLPI supports |
| `PHP_PACKAGES` | see the Dockerfile | Extension packages, without the `php84-` prefix |
| `GLPI_RELEASES` | `https://github.com/glpi-project/glpi/releases/download` | Where the release archive is fetched from |

## Releasing a new GLPI version

1. Read the GLPI release notes, especially for changed requirements (PHP
   version, extensions). `GLPI_MIN_PHP` and `GLPI_MAX_PHP` in
   `src/autoload/constants.php` give the supported PHP range.
2. Edit `appVersion` in `charts/glpi/Chart.yaml` and bump the chart
   `version`.
3. If requirements changed, adjust `PHP_VERSION`, `ALPINE_VERSION` or
   `PHP_PACKAGES` in the Dockerfile.
4. `make test-all`: unit, schema and image tests (see
   [Testing](testing.md)).
5. Commit. CI builds and publishes the image and the chart.

## Publishing and verification

Releases are built per architecture on native runners, gated by Grype and
Trivy scans, signed keyless with cosign, and published with SBOMs, scan reports
and provenance. Tags, verification commands and the reasoning behind the
pipeline are in [Supply chain](supply-chain.md). Whether the current release
has open findings is on the [security status](security-status.md) page.

## Using your own image

`image.repository` / `image.tag` can point at another image only if it keeps
this image's contract:

- application at `/var/www/glpi`, with `public/` readable for the init
  container to copy,
- data paths under `/var/glpi` as in the table above,
- php-fpm in the foreground on `127.0.0.1:9000`, with `ping.path = /fpm-ping`,
- runs as a non-root uid that can write `/var/glpi` (adjust
  `podSecurityContext` if it isn't 33),
- PHP scans `/etc/glpi/php.d` after its own configuration,
- `php bin/console` and `php front/cron.php` available for the migrate init
  container and the cron container.
